# Infrastructure / Cloud 포트폴리오 로드맵

- 기준일: 2026-10-22
- 목표: 2027년 일본에서 Infrastructure / Cloud Engineer 주니어 직무로 전환한다. 기존 쇼핑몰을 workload로 사용해 Linux, network, AWS, 운영·자동화 역량을 증명한다.
- 학습 리듬: 주 3~5시간을 목표로 하고, 바쁜 주에는 2시간 정도를 유지한다. 한 번에 30~60분씩 진행하며 매일 공부하는 것을 조건으로 삼지 않는다.
- 자격증: SAA는 비용 부담을 고려해 보류한다. 우선 hands-on과 설명 가능한 결과물을 만든 뒤, 예산이나 회사 지원이 생길 때 다시 판단한다.

## 목표와 프로젝트 방향

첫 목표는 곧바로 DevOps/SRE가 아니라 Linux, network, server, cloud 운영과 구축을 경험할 수 있는 주니어 Infrastructure / Cloud 직무다. 현재 비IT 경력을 IT 실무경력처럼 표현하지 않고, 검사·이상 확인·원인 추적·결과 기록 경험은 전이 가능한 역량으로 설명한다.

쇼핑몰을 처음부터 다시 만들거나 결제 기능을 모두 복구하는 것이 목적은 아니다. 기존 앱을 최소한으로 실행 가능한 상태로 두고, 클라우드 배포와 보안·비용 판단, 재현성, 모니터링, 장애 분석을 단계적으로 보여준다.

## 진행 스냅샷 — 2026-10-22

### 완료 및 검증

- Java 21과 Maven Wrapper를 확인·복구했고, MariaDB 10.11 기반 local profile로 애플리케이션을 실행했다.
- `./mvnw -DskipTests clean compile`에서 70개 소스의 컴파일 성공을 확인했다. 자동 테스트 코드는 아직 없다.
- 로컬 Gmail 메일 인증 코드 수신과 인증, 일반 회원가입, 가입한 계정의 로그인을 2026-10-20에 확인했다.
- 일반 가입과 OAuth 신규 가입의 기본 역할을 `USER`로 설정했다. 실제 가입·로그인은 확인했지만 테스트 계정의 DB 역할값을 별도로 조회하지는 않았다.
- KakaoPay 결제 준비 조회에서 결제 대기 정보 누락을 404로 처리하고, 결제 대기 정보와 주문 양쪽의 소유자를 확인한 뒤에만 결제 대기 정보를 삭제하도록 수정했다. 컴파일은 확인했지만 실제 KakaoPay 결제는 실행하지 않았다.
- 로컬 실행과 최근 검증 결과를 README에 기록해 커밋·푸시했다. 현재 로컬 `master`와 `origin/master`는 동기화되어 있다.

### 아직 확인할 항목

- 상품 데이터가 없어 상품 목록·상세·장바구니·주문 흐름은 충분히 확인하지 못했다.
- 마지막 페이지의 다음 버튼 수정은 작업 중이며, 브라우저에서 검증하고 별도 커밋해야 한다.
- KakaoPay 승인·실패·취소 callback과 환불 경로는 보안·동작 검증이 남아 있다. 공개 배포 전까지 결제·환불 경로를 비활성화하거나 별도로 안전성을 확인한다.
- OAuth와 OpenAI 연동은 local profile에서 확인하지 않았다.
- 현재 작업 트리에는 `.gitignore`, `mvnw`, 애플리케이션 설정, 페이지네이션 수정과 새 로컬·문서 파일이 커밋되지 않은 상태로 남아 있다. 비밀값과 개인별 IDE 설정을 확인해 변경 목적별로 나눠 커밋한다.

완료 기준: 로컬 실행이 재현 가능하고, 확인된 기능·미검증 기능·미커밋 작업이 구분되어 있다. 결제 기능 복구는 이 기준선의 완료 조건이 아니다.

### 11월 — Linux·network와 첫 AWS 수동 배포

- Linux process, service, port, permission, filesystem, log를 앱 실행과 장애 확인에 연결해 익힌다.
- DNS, HTTP/HTTPS, TCP, subnet, route, security group의 역할을 정리한다.
- 비용 한도와 종료·삭제 절차를 먼저 정하고, 앱을 AWS에 직접 배포해 SSH, IAM, 네트워크 규칙, 로그 확인을 기록한다.
- 과거 EC2/RDS 경험을 활용하되 이번에는 재현 절차, 보안 선택, 비용 판단을 결과물로 남긴다. RDS, ALB, private subnet은 비용과 필요성을 확인한 뒤 확장한다.
- 일본어 채용공고 조사를 시작하고 요구되는 Linux·network·AWS 경험을 기록한다.

완료 기준: 최소 한 번의 수동 배포를 재현하고, 아키텍처와 비용·보안·정리 절차를 설명할 수 있다.

- Docker로 실행환경을 표준화하고, 필요할 때만 Compose로 앱과 DB를 함께 실행한다.
- GitHub Actions에서 build/test를 실행해 실패 원인을 확인한다. 자동 배포는 빌드와 검증이 안정된 다음 진행한다.
- 11월 말~12월에 소규모 지원을 시작해 서류와 기술 질문의 반응을 확인한다. 포트폴리오가 완벽해질 때까지 지원을 미루지 않는다.

완료 기준: 로컬 실행을 재현하고, GitHub 변경에서 자동 build/test 결과를 확인하며, 지원 결과로 다음 보완점을 정한다.

### 2027년 1~3월 — 지원과 운영 증거 보강

- Infrastructure / Cloud 주니어 포지션에 본격 지원하고 면접 피드백에 맞춰 설명과 결과물을 개선한다.
- 이미 배포한 인프라를 Terraform으로 재현하고, CloudWatch 로그·기본 지표·알람 중 필요한 항목을 구성한다.
- 작은 장애 상황 하나를 만들어 탐지·원인 분석·복구·재발 방지를 기록한다.
- Terraform과 모니터링 완성을 지원 시작의 조건으로 삼지 않는다. 좋은 IT offer를 확보하기 전에는 현재 직장을 유지한다.

완료 기준: 프로젝트 하나를 문제 → 선택 이유 → 구현 → 검증 → 한계 순서로 설명하고, 실제 지원 반응에 맞춰 계획을 조정한다.

## 포트폴리오에서 보여줄 결과

1. 오래된 애플리케이션의 빌드와 로컬 실행환경을 복구하고 재현 절차를 정리한 과정
2. Linux와 AWS에 수동 배포하며 네트워크·보안·비용을 판단한 과정
3. Docker와 CI, Terraform, 모니터링을 적용하고 작은 장애를 분석·복구한 과정

기술 이름을 나열하기보다 문제, 조사, 선택, 검증 근거, 남은 한계를 설명한다. 결제 연동은 검증하지 않은 상태를 명확히 표시하고, 핵심 인프라 작업보다 우선하지 않는다.
